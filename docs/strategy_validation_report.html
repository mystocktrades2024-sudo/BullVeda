The Plan

Problem. The signal scanner floods BUYs with two high-volume setups (Trend Continuation, Breakout Expansion) that carry no skill — they make money only from momentum-factor exposure and bleed in chop. The genuine alpha lives in three low-volume setups (VCP / 52-week Breakout / 10-Week Pullback). The mix dilutes — and now appears to erode — edge.

Objective. Quantify what's actually working, then shift the picking mix toward alpha and away from beta — validated, not tuned by feel.

Validation gates — a change ships only if ALL hold

▹Sharpe improves vs baseline AND max-drawdown does not worsen
▹The alpha setups' Wilson 95% lower bound stays positive at n ≥ 30
▹Consistent across folds — not one lucky window (principle 5 regime-conditioning, principle 20 no acting on noise)

API / quota budget

Backtesting is cheap here: OHLCV bars are cached to parquet (2,184 files on disk) and reused across every variant; only params change between A/B and walk-forward runs. EODHD usage today 30,013 / 100,000 (70K headroom). Whole effort ≈ a few hundred one-time calls — the real cost is wall-clock compute, not quota.

NULL result — and it was predicted. Arm B is bit-for-bit identical to Arm A. The breakout-bypass moved nothing in the backtest, because the backtest selects trades by top-5/day by SCORE, not by verdict — flipping a WATCH label to BUY doesn't change which trades are taken. Both arms even show 0 BUY / 323 WATCH, so the bypass had no on-screen effect here either. The backtest is the wrong instrument for this change. The bypass is real and unit-verified (VCP EXTENDED → BUY in make_decision); its effect is on (a) the scanner — surfacing alpha setups as BUY, and (b) the verdict-gated executor — which only trades BUYs. Neither is captured by a score-ranked backtest.
Bigger finding the A/B exposed. The 252d baseline config (score≥65/RS≥75) is net losing (PF 0.70) AND issues 0 BUY across 323 signals — yet the live system issued 12 BUYs today. So the backtest's verdict path diverges sharply from live (much stricter / different gate set). That's a backtest-fidelity gap: until the backtest reproduces live BUY behaviour, it can't validate any verdict-level change. This is now the real blocker, ahead of the breakout-bypass.

Cost / lesson

Two 6-hour full-fidelity runs (12 core-hours) returned an uninformative null — the instrument didn't match the change. Confirms: (1) the structural-target backtest path needs a perf pass + a [day N/252] progress log before any walk-forward; (2) verdict-level changes need a verdict-gated backtest (take only BUY-verdict trades) or an executor replay, not the score-ranked portfolio backtest.

5d · Robustness battery — the reusable method  reproducible

So the forward re-run is set up to run itself, the four checks any future feature claim must pass before it counts as evidence:

  1. Collinearity — set-overlap of candidate buckets; ≥~80% overlap = one lever, not N.
  2. Per-day independence — % of a bucket from its top-2 days; high % = day-batch artifact, not edge.
  3. Median of daily PFs — immune to one blow-out day that distorts the pooled PF.
  4. Multivariate control — re-test each lever within the others' clean complement; the score-band “edge” vanished here.
Forward plan (the actual validation). Re-run this exact battery on post-06-13 resolved trades — genuinely out-of-sample, under the current ranker + BUY-floor config — in ~1–2 weeks once those swings resolve. Two questions: (a) does the live system capture the Breakout/T1 lever forward, and (b) does the breakeven choppy baseline improve under the new gates? Until then: observe, do not change. Scripts: scripts/signal_walkforward_oos.py (OOS A/B) + the inline robustness battery (collinearity / per-day / median-daily-PF / multivariate).
